# Dataset Documentation

This project uses three data sources, each with a dedicated adapter in
`src/data/`. They are **not interchangeable** — do not treat results on
one as equivalent to another.

---

## 1. AMLSim (primary dataset)

**Source:** [github.com/IBM/AMLSim](https://github.com/IBM/AMLSim)
**License:** Apache 2.0 (simulator code). Generated data is synthetic —
no real financial data is involved, but AMLSim is not a pre-packaged
downloadable dataset.

### How to get it (no shortcut — do not skip this)

AMLSim is a **simulator**, not a static file. You must run it yourself:

```powershell
git clone https://github.com/IBM/AMLSim.git
cd AMLSim
# Follow AMLSim's own README: install Java 8+/Maven, configure
# paramFiles/<size>/conf.json, then:
python3 scripts/transaction_graph_generator.py conf.json
sh scripts/build_AMLSim.sh
sh scripts/run_AMLSim.sh conf.json
python3 scripts/convert_logs.py conf.json
```

This produces (under AMLSim's `outputs/<sim_name>/` or `tmp/<sim_name>/`
depending on version):
- `transactions.csv`
- `accounts.csv`
- `alert_accounts.csv`
- `alert_transactions.csv`

Copy `transactions.csv` (and optionally `accounts.csv`) into:
```
data/raw/amlsim/
```
then set `dataset.active: amlsim` in `configs/config.yaml`.

### Confirmed output schema (verified against the IBM/AMLSim wiki)

`transactions.csv`: `tran_id, orig_acct, bene_acct, tx_type, base_amt, tran_timestamp, is_sar, alert_id`
(`alert_id = -1` means the transaction is not part of any AML typology.)

### Preprocessing assumptions made by `AMLSimAdapter`

- `tran_timestamp` is a **simulation step index**, not a wall-clock
  timestamp. The adapter converts it to a synthetic UTC date anchored
  at a configurable `sim_start_date`, one day per step by default.
  **Check your run's `conf.json` step granularity** — if it isn't
  daily, pass a different `step_unit` to the adapter.
- `alert_id` is mapped to both `scenario_id` and `ring_id` in our
  canonical schema, since each AMLSim alert groups the full set of
  transactions belonging to one generated laundering typology
  instance — this is a reasonable but adapter-level assumption, not a
  property AMLSim itself asserts.

## 2. Elliptic (secondary/external validation dataset)

**Source:** originally released via Kaggle ("Elliptic Data Set") and
academic mirrors; access terms vary by mirror and may require
registration.
**Reference:** Weber et al., "Anti-Money Laundering in Bitcoin: Experimenting
with Graph Convolutional Networks for Financial Forensics" (2019).

### Structural mismatch with AMLSim — read this before using it

AMLSim's graph is **account → account** (a node = bank account). The
original Elliptic dataset's graph is **transaction → transaction** (a
node = one Bitcoin transaction on the UTXO graph; features are
PCA-anonymized, no raw BTC amount is published). `EllipticAdapter`
maps Elliptic's edges onto our `sender`/`receiver` columns for
structural compatibility, but:
- `amount` is left as `NaN` — it does not exist in the public release.
- "sender"/"receiver" mean upstream/downstream **transaction**, not
  account. Do not narrate Elliptic-derived output using
  account-level language.
- `timestamp` is reconstructed from Elliptic's integer `time_step`
  (1–49), approximated at ~2 weeks/step per the original paper — an
  approximation, not a real timestamp.

### Elliptic2

The literature review (Review-1 PPT, slide 5, ref. [7]) cites a 2026
paper using **Elliptic2**, which has subgraph-level money-laundering
labels rather than per-transaction classes — a different release
format from the original Elliptic. `EllipticAdapter` targets the
**original** Elliptic release only. Wiring up Elliptic2 specifically
is a documented follow-up, not something to guess at from the
original schema.

### Expected raw files
```
data/raw/elliptic/elliptic_txs_features.csv   (no header)
data/raw/elliptic/elliptic_txs_classes.csv
data/raw/elliptic/elliptic_txs_edgelist.csv
```

## 3. Demo / Synthetic dataset (default, no download required)

Generated by `src/data/demo_generator.py` via:
```powershell
python scripts/generate_demo_data.py
```

**This is synthetic data created for this project, generated fresh
each run from a fixed seed. It is not AMLSim data, not Elliptic data,
and must never be presented as either.** Every artifact derived from
it (reports, dashboard views, API responses) must carry a
"DEMO / SYNTHETIC DATA" label — enforced starting in later
phases (backend/frontend), not yet implemented as of Phase 2.

Contents: background "normal" transaction traffic among ~150 ordinary
accounts, plus a configurable number of embedded ring scenarios. Each
ring scenario is built stage-by-stage (fan_in → layering → fan_out →
repeated_intermediary → circular_flow) with real timestamps, and its
full ground truth — including `observable_time`, the day its
structure becomes fully present — is written to
`data/demo/ring_ground_truth.json`. This is what the lead-time engine
(a later phase) will evaluate warning times against; it is generated
from the data, never hard-coded.

## Canonical schema (all three sources normalize to this)

| Column | Type | Notes |
|---|---|---|
| `transaction_id` | string | globally unique |
| `sender` | string | account (AMLSim/demo) or upstream tx (Elliptic) |
| `receiver` | string | account (AMLSim/demo) or downstream tx (Elliptic) |
| `amount` | float | `NaN` for Elliptic |
| `timestamp` | datetime (UTC) | reconstructed/approximated for AMLSim & Elliptic — see notes above |
| `label` | int8 | 1 = laundering-labeled, 0 = normal, -1 = unknown |
| `scenario_id` | string | typology/ring grouping, "" if unavailable |
| `ring_id` | string | same as scenario_id here; kept separate for future disambiguation |
| `dataset_source` | string | `"amlsim"` \| `"elliptic"` \| `"demo"` |

See `src/data/schema.py` for the authoritative definition and
`src/data/*_adapter.py` for how each source maps onto it.
